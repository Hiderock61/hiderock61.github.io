01 / JOB TYPE

NEWをそのまま上書きせず、原本・正規化・差分・更新候補を分離する

定期更新で危険なのは、表記揺れによる誤照合、重複キー、NULLの意味違い、DELTAを全件スナップショットと誤認した大量DELETEです。そこで、照合前に更新契約とSOURCE_MODEを固定しました。

IMPORT → VALIDATE → NORMALIZE → MATCH → DIFF → CLASSIFY → STAGING → VERIFY → EXPORT。

02 / PROCESS

一意キーで照合し、曖昧なものだけREVIEWへ

01

更新契約

SOURCE_MODE / Schema / Key / NULL / DELETE規則を固定。

02

正規化

全角半角、空白、電話、email、日付、enum、金額を項目別に処理。

03

キー検査

欠損・重複・型異常を照合前にREVIEWへ隔離。

04

差分分類

ADD / UPDATE / DELETE / REVIEW / SAMEへ分類。

05

STAGING

本番へ直接書かず、更新候補とDIFFを生成。

06

再実行

同じNEWを再投入してADD / UPDATE / DELETE = 0を確認。

03 / FAILURE → STOP / REVIEW

誤DELETEと誤更新を壊し試験で止める

FAULT 01 / DELTA

変更分15件だけをNEWとして投入

SNAPSHOTと誤認すれば985件を削除しかねない条件。

→ SOURCE_MODE=DELTAではDELETE=0。

PASS

FAULT 02 / DUPLICATE KEY

同じcustomer_idを競合させる

→ 自動UPDATEせずREVIEWへ隔離。

PASS

FAULT 03 / NULL

既存emailを空欄へ

意味不明の非NULL→NULLを自動適用しない。

→ REVIEW。

PASS

FAULT 04 / SCHEMA

customer_id列を欠損

→ SCHEMA_MISSING_COLUMNSで処理前にFATAL停止。

PASS
