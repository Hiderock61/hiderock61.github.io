01 / PURPOSE

完成画面を一発で作るのではなく、改善できる制作工程を作る

水道修理サイトは、見た目を整えるだけでは成立しません。利用者は「いくらかかるのか」「何をされるのか」「どこまで来てくれるのか」「問い合わせた後どうなるのか」を短時間で判断します。

そこで本制作では、最初から完璧なデザインを狙わず、まず動く初回版を作成。その後、実在サイトの構造・視覚・文言を観察し、iPhone実機で確認しながら改善しました。

制作の中心に置いたのは、AIの出力をそのまま採用することではなく、画面を見て違和感を言語化し、次の小さな修正へ変換することです。

「作る → 見る → 違和感を特定する → 小さく直す」を一つの制作技術として扱いました。

TARGET / LOCALIZATION

全国向けではなく、「近所の修理屋を探す人」のために作る

みず番は、大手の全国展開サービスより規模や知名度で優位に立つ設定ではありません。想定したのは、杉並区・中野区で「できれば近所の水道修理業者へ相談したい」と考える利用者です。

そのため、サービス範囲を広げることより、対応地域、料金、作業内容、担当者、問い合わせ方法がすぐ分かることを優先しました。受付と作業担当を分けない小規模事業者型とし、相談内容が現場担当へ届くまでの情報伝達を短くしています。

水道トラブルは、落ち着いてWebサイトを鑑賞する場面ではありません。スマートフォンを開いた時に、「自宅は対応地域か」「いくらくらいか」「何をしてくれるのか」「どこを押せば連絡できるか」を短時間で判断できる必要があります。

デザインも、洗練されたブランドサイトを目標にはしませんでした。青・白・黒、大きな文字、大きな料金表示、赤い電話ボタンなど、生活サービスとして意味を理解しやすい視覚表現を優先しています。Web操作に慣れていない利用者や高齢の利用者を含め、幅広い年代がスマートフォンで迷いにくいことを狙いました。

少しベタに見える視覚表現も意図的なUI選択です。流行性より即読性を優先しました。

02 / OBSERVE

実在サイトから、役割ごとに学ぶ

一つのサイトを丸ごと真似るのではなく、「何を参考にするか」を分解しました。

Bears系サイト

スマホのメニュー順と、本文を上から読む順番は同じでなくてよいと整理。メニューは移動装置、本文は説得と理解の順番として分離しました。

Water King

強い青・白・黒、大きな見出し、カード、固定CTAなど、水回りサービスらしい視覚の強度を参考にしました。

水道トラブル119番

抽象的な安心表現より、症状・作業内容・料金・流れを具体的な言葉で見せる方向を参考にしました。

AIからの提案

48px前後の操作領域、カードの次項目が少し見える横スクロール、FAQ開閉、iPhoneのsafe-areaなど、モバイルUIの候補を取捨選択しました。

03 / PROBLEMS

iPhoneで見て初めて分かった問題

コード上で成立していても、実機で見ると「使いにくさ」や「弱さ」が具体的に見えてきました。

01

CTAが重複していた

Hero内の問い合わせ導線と固定下部CTAが競合。入口で同じ行動を何度も迫る状態になっていました。

02

トラブル表現が抽象的

「水回りのお困りごと」だけでは、自分の症状と一致するか判断しにくい状態でした。

03

説明セクションが文字中心

「説明してから直す」という強みが、文章だけでは瞬間的に伝わりませんでした。

04

作業事例が結果だけ

料金と結果はあっても、確認から施工まで何をするのかが見えず、依頼後を想像しにくい状態でした。

05

情報の順番が弱い

トラブル一覧の位置など、サービス理解の流れとして読むと前後関係が不自然な部分がありました。

06

写真は実機で荒さが露出

SVG内へ縮小ラスターを埋め込む暫定処理により、iPhoneではブロック状の粗さが見えました。表示確認が画像工程の検品にもなりました。

04 / PROCESS

全面改修ではなく、差分を積み上げる

PHASE 01

まず、動く初回版を作る

目的
考え続けるより、iPhoneで見られる実物を先に作る。
実装
Hero、料金、安心、事例、流れ、トラブル、エリア、担当者、FAQ、問い合わせ、会社情報を1ページに配置。
判定
構造は成立。ただし一般的なAI生成サイトらしく、視覚と文言がまだ弱い。
PHASE 02

視覚の言語を水道修理サイトへ寄せる

観察
水回り系サイトの強い青、大きな料金表示、固定CTA、カード構造を比較。
修正
青・白・黒を中心に統一し、電話は赤、Web相談は青として役割を分離。
効果
業種が一目で分かり、料金と問い合わせ導線の優先順位が明確になった。
PHASE 03

「安心」を抽象語から具体情報へ変える

問題
安心・丁寧などの言葉だけでは、何をしてくれるのか分からない。
修正
症状、料金目安、作業時間、部品代、作業前説明、対応エリアを具体化。
代表コピー
「説明してから、直します。」を中心メッセージとして整理。
PHASE 04

作業事例を「施工後」から「工程」へ拡張

問題
事例カードだけでは、依頼後に何が起こるか見えにくい。
修正
CASE 1〜3を開閉式にし、点検・説明・施工・確認の流れを番号付きで表示。
狙い
料金だけでなく「どう直すか」を読める事例にする。
PHASE 05

iPhoneの違和感を小さく潰す

修正例
CTA重複の解消、トラブル位置変更、横スクロールの次カード見せ、FAQ配色調整、safe-area対応。
考え方
一度に完成させず、実機で一つずつ判定して次の差分へ進む。
結果
スマートフォンで読む順番と、押す場所が徐々に明確になった。

05 / ITERATION

バージョンは、完成度ではなく判断の履歴

v0.1

基本構造

サービスサイトとして必要な主要セクションを配置。

v0.1.1

CTA整理

Heroと固定CTAの重複を減らし、トラブル表現を強化。

v0.2

青・白・黒へ統一し、水道修理サイトとしての視認性を上げた。

具体化とスマホUI

文言、料金、固定CTA、バッジ、横スクロール、FAQなどを実機基準で調整。

v0.2.5〜6

事例と情報順

トラブル位置を変更し、作業事例を開閉式の工程表示へ拡張。

PHOTO

画像工程の実機検品

写真追加後、iPhoneで粗さを発見。SVG内の縮小ラスターを使う暫定処理ではなく、元JPEGを直接扱う方針へ修正した。

06 / METHOD

この制作で固まった「その方法©️」

完成品を頭の中だけで設計し続けず、観察と実機判定を制作工程そのものにする。
実在サイトを見る→構造を抜く→小さく実装→iPhoneで見る→違和感を1〜3個に絞る→差分修正→再検品
写真工程でも同じ。 コード上では「表示できた」で終わっても、実機では画質劣化が見えた。そこで原因を画像形式・埋め込み方法まで逆算し、次の施工条件へ変換した。

07 / RESULT

最終的に残ったもの

情報の透明性

料金、作業時間、部品代、対応エリア、施工の流れを画面上で確認できる構造にしました。

スマホ中心の導線

固定電話・Web相談、メニュー、カード、FAQなどをiPhoneで操作する前提で調整しました。

改善できる制作能力

AIで作ること自体ではなく、実物を検品し、問題を分解して次の差分へ変える工程を制作実績として残しました。

利用者と業種に合わせたデザイン

見た目の新しさではなく、水道トラブル時の利用場面と地域利用者を基準に、文字サイズ、色、料金表示、CTA、情報量を決めました。

08 / VIEW

完成版サイトを見る

ケーススタディは制作の裏側、完成版は利用者が実際に触る画面です。両方を見ることで、どこを観察し、何を変えたかを確認できます。
